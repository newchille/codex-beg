# ADR-0008: Treat the local control plane as a privileged boundary

## Status

Accepted

## Context

Codex BEG binds its MCP and desktop-control HTTP services to loopback, but loopback alone does not imply that every local process or renderer-originated request should be trusted. The desktop renderer is intentionally sandboxed and may display untrusted repository-derived data, while administrative routes can approve operations, alter workspace registrations, and trigger recovery actions.

Workspace registration is also a capability expansion: adding a new absolute root changes which local files the agent may inspect or mutate. That must not be silently available to MCP callers or to compromised renderer code.

## Decision

Separate the local control plane into explicit trust boundaries.

- `/admin/*` and `/events` require a random per-session admin token generated by Electron main.
- The token is delivered to Agent Host over a one-shot anonymous stdin pipe and is never placed in argv/environment or exposed through preload or renderer APIs.
- Agent Host compares the admin token using a timing-safe equality check.
- `/healthz` remains unauthenticated on loopback so local diagnostics can determine whether the Agent Host is alive and which tool catalog is running.
- Renderer code is not treated as a trusted source of absolute filesystem paths.
- Native Electron main owns the workspace folder picker. Renderer IPC communicates only intent such as workspace kind or parent workspace ID.
- MCP `workspace_add` and `workspace_register` are classified as `CAPABILITY_GRANT` operations and require Approve Once before expanding the registered filesystem boundary.
- Approvals initiated from the desktop require a native Electron confirmation dialog before Electron main calls the authenticated admin approval endpoint.
- Approval state is operation-hash bound, expiring, and single-use as before.
- `/mcp` remains loopback-accessible without a custom application header for now. Stronger endpoint identity should use a Secure MCP Tunnel-compatible documented mechanism rather than an invented header.
- OpenAI's current Secure MCP Tunnel documentation and `openai/tunnel-client` implementation explicitly support MCP-side mTLS for Streamable HTTP using `MCP_CLIENT_CERT` / `MCP_CLIENT_KEY` (or `--mcp.client-cert` / `--mcp.client-key`) plus custom CA trust when required. This is the preferred future endpoint-identity path: https://developers.openai.com/api/docs/guides/secure-mcp-tunnels and https://github.com/openai/tunnel-client/blob/master/docs/connectors.md
- Codex BEG must not silently generate or install a private CA/client identity on a managed workstation. Enabling MCP-side mTLS requires explicit operator-provisioned server certificate/key and trusted client CA material, followed by tunnel-client configuration and live acceptance testing.

## Consequences

- Another ordinary local process cannot call administrative routes without possessing the in-memory app-session token.
- A compromised renderer cannot obtain the admin token or submit an arbitrary absolute path through the preload bridge.
- Expanding MCP filesystem capability becomes an explicit user decision rather than an implicit side effect of tool access.
- Native approval UI becomes a trusted confirmation boundary above renderer content.
- Loopback MCP exposure is still not considered equivalent to strong client identity; transport authentication remains a separate future hardening phase.
- Restarting the Desktop app rotates the admin token automatically because the token is session-scoped.
